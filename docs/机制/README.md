## 组织原则

- 按完整功能建档，例如回忆值、陷落条件、时停搬动检测；相关文件、函数和状态汇入同一条目。
- 初步盘点区分实际实现、空模板、停用代码和调试辅助。函数存在或注释声称有效，均不能直接作为本机兼容性结论。
- 每轮原则上审查一个机制，连同必要依赖查清；旁支问题先登记，避免无限扩大范围。
- 区分用户说明、源码事实、注释线索和参考推断。原设计意图不明时保留问题，不替用户补定设定。
- 源码核对、运行验证和处理决定分别记录。未运行验证不写“测试通过”。
- 本体更新后，依据已记录的接口依赖定位复查范围；修改机制时同步更新条目和总表。

## 单项审查流程

1. 从口上源码还原现有行为，找齐相关函数和状态。
2. 借助知识库定位本体机制；按需与内置中文模板比对，区分通用骨架和自定义逻辑、寻找新接口线索，再核对当前源码的定义、调用者、条件和执行顺序。模板差异不直接视为问题。
3. 检查相关边界，如未初见、睡眠、时停、目标切换、跨日和读档；按实际依赖选择。
4. 比较现有做法与本体接口，评估兼容性、行为差异和维护成本。
5. 写入详细条目、更新总表；无法确定的内容进入待定事项。

## 单项记录规范

详细条目按以下结构填写，简单机制可以简写，但不能省略关键证据和未确定项：

1. **身份与进度**：稳定编号、机制名称、所属类别、源码审查进度、运行验证进度和处理决定。
2. **用途与意图**：玩家可感知的行为、解决的问题，以及设计意图的来源。
3. **当前实现**：入口、调用顺序、触发条件、主要分支、返回值和效果；列出相关函数。
4. **状态生命周期**：变量或槽位、作用对象、初始化、写入、读取、恢复和清除位置，以及跨回合和存档行为。
5. **本体依赖与兼容性**：依赖的接口、覆盖的行为、当前本体可用的替代方式及证据；如参考模板，记录对应文件、函数、关键差异及其解释，不明的历史来源保持未确认。
6. **问题与建议**：已确认问题、参考推断、保留或修改建议、预期行为差异和旧存档影响。
7. **核验与复查依据**：源码路径、函数标签、必要行号、核验日期、口上和本体提交标识及相关工作树改动；涉及引擎扩展时记录引擎版本。行号仅作快照参考。
8. **验证与后续开发**：源码检查结果、实际运行的场景与结果、尚未验证的内容、后续扩展注意事项及关联待定事项。

总表采用简短摘要并链接到详细条目，详细证据以条目为准，避免重复维护大段内容。

## 修订方案与空间预算

已实现**按料理编号自动寻址的63位分块位图**，占当前角色的CFLAG1252～1259，共8个槽；其中1252～1257是原料理记录区，只多占1258、1259两槽。其余预留空间保留给其他机制，不为料理划走1401～1999。

每个槽只用bit0～62，第63位始终为0；每块有63个记录位。8块共504位，可表示料理编号101～604的地址，其中空号、DEBUG菜和保留编号不成为正式收集项。

| CFLAG槽位 | 可表示的料理编号 |
| --- | --- |
| 1252 | 101～163 |
| 1253 | 164～226 |
| 1254 | 227～289 |
| 1255 | 290～352 |
| 1256 | 353～415 |
| 1257 | 416～478 |
| 1258 | 479～541 |
| 1259 | 542～604 |

本轮核查：当前QOL目录342个ID，含183个普通、159个固有，最大560，全部可表示。当前本体人物数量上限200，原生角色料理登记按1～199处理；对应401～599，也在8块容量内。10块是中途估算，核算后当前8块即可，不预留额外块。

## 编号到记录位的固定公式

```text
相对编号 = 料理ID - 101
块号     = 相对编号 / 63       （整数除法）
位号     = 相对编号 % 63
CFLAG槽  = 1252 + 块号
```

必须先检查编号范围，再做除法、取余和访问。对101～604，块号为0～7，位号为0～62。

| 料理ID | 槽位 | bit |
| --- | --- | --- |
| 104 | 1252 | 3 |
| 163 | 1252 | 62 |
| 164 | 1253 | 0 |
| 345 | 1255 | 55 |
| 436 | 1257 | 20 |
| 599 | 1259 | 57 |
| 604 | 1259 | 62 |

公式不依赖目录排序、名称或普通/固有分组；无需再为183道普通菜手写位置映射，新补14项自然有地址。新增605及以后有效ID时，每多覆盖63个连续编号只需增加一块，但须先核对相邻槽位占用；本方案没有自动扩容或占用1260以后槽位。

## 数据含义和有效记录

- 每一位只表示是否曾与本口上角色共同制作：0为未记录，1为已记录；重复制作保持1。暂不保存次数、日期或完整事件日志。
- 普通和固有料理共用8块，不再有独立C1/C2/C3；分类是读取和统计时对料理ID的解释，不是存储分段。
- 名称、材料、口味、分类仍由本体资料及实际料理实例提供，不复制进存档；同ID的动态名称和菜单覆写仍共用该ID的记录，自定义食谱文本标记继续单独保留。
- 299为DEBUG专用、400为保留编号，不允许作为正式收集写入；普通空号不因有地址就成为料理。记录入口必须已经确认这是实际成功制作的有效食谱。
- 目录有效性和制作资格在记录入口/目录层确认，不在每次查询标记时反复调用DISHDATA或查库。固有料理须允许本体支持的口上覆写，不能仅因QOL缺少基础条目就一律否定实际已制作的自定义食谱。

## 统一访问与统计

已在现ERH的CFLAG栏目登记AME36料理历史常量，包含记录起点、块数、每块有效位数、首个/末个可表示ID、固有编号基准、自身和DEBUG编号。所有业务调用统一接口，动态属性范围限定1252～1259。

对外使用统一的记录、查询和统计接口：

| 操作 | 约定 |
| --- | --- |
| 记录 | 传角色登记索引与已确认的料理ID；检查角色/编号，按公式SETBIT；可返回新记录/重复/输入无效 |
| 查询 | 同样计算槽位和位号，用GETBIT返回0/1，不改变状态或TARGET |
| 统计 | 分别计算普通料理数、其他固有料理数、本角色料理是否记录；这些是临时派生值，不另占存档槽 |
| 初始化/重置 | 使用新档CFLAG零值及本体既有整角色重置；不新增清空接口或转换逻辑 |

该记录区只分配给本口上角色。登记索引不能硬编码为36，角色编号NO36与运行中的角色数组下标须分清；不得调用这些接口写角色37的地点探针空间。所有需要变更TARGET的外层路径保持原有恢复责任，数据接口本身不换TARGET。

普通统计取正式普通ID范围/目录，固有统计取有效固有ID；本角色436单独查询，其他固有去除436，避免重复加分。列表按本体目录排序显示，但标记始终按ID查询，不能按显示序号累加bit下标。

不要将8个CFLAG整数相加当作数量或“是否为空”：它们是位图。数量通过记录位统计，空记录可逐块检查非零。跨分类的边界可能位于同一块，不能把整块简单认成全部普通或全部固有。

每块正常值均非负且最多有63位。料理侧无需处理符号位，也不再依赖“负数右移直到归零”的计数前提；现通用AME36_BINARY_SUM仍可能被酒等其他机制调用，是否改它另按其真实调用范围决定，不将本方案未实施写成R007已修复。

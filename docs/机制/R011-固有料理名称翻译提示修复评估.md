## A：纯口上侧修复

### 拟修改范围

在`M_KOJO_K36_3_自定义机制_杂项.ERB @M_KOJO_AME_CHECK_K36_CHARADATA`的SPECIAL_MENU分支，为实际设定的DISH_NAME登记同名翻译。登记放在DISH_NAME赋值后、返回食谱数据前，不依赖相识、学习完成或成功做出料理：警告发生在浏览/教学菜单时，这些较晚条件都会错过第一次显示。

可以在该分支用LOCAL接住参数化SQL表达式的返回值；这仍只使用LOCAL:0，现尺寸1足够。若为了复用抽辅助函数，仍遵守尺寸和注释纪律。不得让SQL返回值覆盖分支应返回的RESULT=1或RESULTS=主食；推荐在SQL操作完成后保持/写回食谱类型，并由原RETURN 1结束。

### 登记规则

仅登记本口上明确提供的最终中文名称，不扫描所有食谱并给所有未知名自动建同名项。使用参数化SQL，参数名与译文均传DISH_NAME，避免手工拼接名称。

候选SQL：

```sql
INSERT INTO TASTE_MAP(k, v) VALUES(@0, @1)
ON CONFLICT(k) DO UPDATE SET v = excluded.v
WHERE TASTE_MAP.v IS NULL OR TASTE_MAP.v = ''
```

语义：缺键时新增；原值空/NULL时补齐；已有非空翻译时保留，不强制REPLACE覆盖。若原值已经同名，重复调用无变化。菜名含单引号也由本体SQL_P_EXECUTE_NONQUERY参数化绑定处理。当前本体已有同类ON CONFLICT参数化调用；本方案未在Emuera中运行。

每次SPECIAL_MENU回调都执行这项幂等操作，规模只是一条名称记录。不增加CFLAG、SAVEDATA、FIRSTTIME或普通DIM的“已经登记”缓存：内存翻译库的生命周期与游戏存档不同，保存了完成标记并不能保证下一次进程里仍有这条翻译。

### 影响与限制

- 不修改本体ERB、XML和plugins/qol_data.db，不改变ID436、材料、口味、说明、历史、贡献或相识门控。
- TASTE_MAP是运行期共享表，并非口上私有表。其他代码查询相同字符串时也能看到该条目；保留已有非空译文可以减小冲突，但不提供按口上命名空间隔离。
- 正常关闭/重建连接后，下一次SPECIAL_MENU再登记即可；不需要迁移旧存档。登记不能只放在INIT首次标记内。
- 不使用SQL_CONNECT或CREATE TABLE去“确保”本体翻译库存在；在不正确的早期调用点自行重建会改变库的所有权和初始化顺序。若未来改调用链，须复核这一前提。
- 日后更换自定义菜名，新名称可在回调时登记；旧名称仍可能被已有料理实例引用，不应自动删除旧映射。当前口上不支持运行中随意切换，不扩展为全套多口上卸载管理。

## 为什么不优先修改DISHNAME_TR的判断

直接删除警告、只要含汉字就跳过、只要是固有料理就跳过，都会混淆已本地化自定义名与真正缺失的内置翻译。把DISH_COMMENT改成“※正在招募中！！※”则会破坏正常说明，属于错误规避。

只在该函数硬编码“琥珀渔夫派”白名单虽然能消除本例提示，但把私人菜名塞进通用逻辑，比XML数据补项更难维护，覆盖收益也相同。

如果目标升级为本体通用支持“这是最终显示名，无需翻译”，可以设计显式注册接口或元数据；它是另一个工作量等级。新标记必须区分普通/原生/口上覆写、缓存和DISHDATA_ORIGINAL路径，并处理RESET_DISH、料理字段备份恢复以及存读档。仅新增一个未保存的布尔变量，可能在切菜/查询/读取存档后串到其他料理或丢失。当前不建议为了这一条名称引入整套状态生命周期。

另有一个相关但独立的现状：DISHNAME_TR接受显式ARGS，但查不到时固定返回当前DISH_NAME，而非归一化后的ARGS。本体LEARNING_SP_DISH等确有显式参数调用。A/B都通过让本例名称命中翻译表避开该分支，但没有修复这个一般性回退问题；若未来维护通用翻译函数，应单独核对并处理，不在本例顺带扩大修改。

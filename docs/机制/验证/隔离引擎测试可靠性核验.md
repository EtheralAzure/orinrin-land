# 隔离引擎测试可靠性核验与使用说明

日期：2026-11-14。结论：小规模可靠性自检通过，可登记为本项目函数级测试的长期备选。它不替代完整游戏调用链、真实依赖、存读档、界面和玩法验证，也不要求每轮任务强制运行。

## 默认静音补充（2026-11-14）

共享执行器现默认使用可恢复的Windows系统提示音静音守卫，不屏蔽正常错误输出。测试期间其他系统提示音也一起静音，系统主音量与普通应用声音不变；结束后恢复原Mute状态。静音下18项可靠性检查和原2093项回归再次通过，另有4项恢复/并发/所有者退出检查，见[静音与恢复核验](隔离测试静音与恢复核验.md)。如不能确认静音，不启动测试引擎。

## 自检内容与结果

“反例通过”表示框架成功将它判为不通过，不表示有错误的ERB被认可。

| 检查 | 方法 | 预期与最终结果 |
| --- | --- | --- |
| 正常例 | 实际引擎执行已知函数，完成1条断言 | 通过 |
| 断言失败 | 将预期42故意改成43 | 即使退出码0，也拒绝 |
| 语法错误 | 函数体写入不完整表达式 | 拒绝，记录引擎错误/未完成/超时 |
| 完成后运行时错误 | 先输出正常汇总，再故意数组越界 | 拒绝，正常汇总不能覆盖后续错误 |
| 完成后零除警告 | 先输出正常汇总，再执行零除 | 即使退出码0且失败数0，也拒绝Lv1警告 |
| 超时 | WAIT等待，无人输入 | 按界限终止自己的子进程并拒绝 |
| 缺失汇总 | 正常退出但不写结束信息 | 拒绝 |
| 旧结果 | 在新运行目录预放“通过”文件，甚至使用同一运行标识，再运行不输出汇总的程序 | 先删除旧文件，最终拒绝 |
| 空套件 | 输出0条断言而预期1条 | 拒绝 |
| 源文件改变 | 封存指纹后改动测试专用源文件 | 启动前拒绝，不修改正式源码 |
| 夹具被改 | 封存指纹后改动待执行文件 | 启动前拒绝 |
| 非零退出码 | 基于真实正例产物，对判定器注入退出码17 | 拒绝 |
| 错运行标识 | 基于真实正例替换标识 | 拒绝 |
| 汇总相互冲突 | 基于真实正例令保存文件与日志的断言数不同 | 拒绝 |
| 假零失败汇总 | 在真实正例的零失败汇总旁加入明确失败输出 | 拒绝 |
| 缺保存文件 | 保留真实正例日志，去掉保存汇总 | 拒绝 |
| 重复标签 | 给抽取器两个同名函数 | 拒绝，不静默取其中一个 |
| 残留脚本 | 检查所有运行后的项目脚本 | 仍只有根目录原8份可加载ERB/ERH，无活动夹具 |

前11项是实际引擎运行或运行前完整性校验；其中源/夹具失配在启动前被拒绝。随后5项是使用实际正例证据的判定器故障注入，最后2项是抽取及归档检查。18不是18个完整游戏场景。

机器报告：[isolated_engine_reliability_result.json](../../../tmp/isolated_engine_reliability_result.json)。每个运行/启动前检查的独立目录、结果和理由都在该报告中；报告还保存共享模块及自检脚本的SHA-256，确认自检过程中工具未变。

## 自检发现并修正的问题

原脚本主要依赖“找到零失败汇总且未超时”，没有把退出码、诊断输出、运行身份和源码完整性统一纳入。现已改为同一个严格判定入口。

自检中另抓到一个本机具体行为：**零除是Lv1警告，程序仍可能以0退出**。只看汇总/退出码会误报通过。现在默认把本次诊断中Lv1及以上告警、运行异常和显式失败输出都纳入不通过；零除反例已验证被拦住。

本机`FORCE_QUIT`另会写入一段“Script execution terminated”的调试轨迹。它是正常退出的控制流程痕迹，不能简单用“日志出现ERROR”判断全部失败，也不能泛化忽略所有错误。当前仅在以下条件都成立时，排除这段精确轨迹：退出码0、未超时、日志与保存文件都有匹配本次标识/预期断言数的完成信息、轨迹为已核实的空调用栈且ErrorLine=null。其他错误/警告继续保留，断言失败仍为失败。这个窄范围例外有明确日志签名，更换引擎后必须重新核查。

## 当前通过条件

每次运行生成唯一目录和随机运行标识，执行前清理该目录的结果文件。只有同时满足以下条件才通过：

1. 源文件、生成的ERB/ERH/CSV输入与封存指纹相符，执行前后都检查；引擎副本与记录的原引擎SHA-256一致。
2. 引擎确实启动、未超时且退出码为0。
3. 日志包含本次开始标记；日志和保存文件都有同一个本次结束标记，且二者一致。
4. 断言数量为正且恰等于套件预先声明的数量；失败数0，且没有失败明细或不允许的引擎诊断。
5. 复制的引擎已删除，夹具脚本已归档，清理失败也使结果不通过。
6. 当前默认音频守卫已确认静音并恢复原状态、尾音已安静；静音或恢复失败同样不通过。

源码、输入、引擎指纹、抽取函数指纹、退出状态和归档清单均进入结果文件。报告采用临时文件后替换的方式写入；M006和自检入口会先把最新报告标为未完成，避免中止后继续展示上次成功结果。

默认判定宁可要求复查也不静默放过问题。已知的非错误告警如需例外，必须先核实具体引擎行为与覆盖条件，不能为了“绿灯”直接降低检查级别。

## 日常使用

正常业务修改时，按任务风险选择适合的测试，不必每次自检测试框架。

```powershell
python tmp/m006_history_engine_check.py
```

这是当前料理历史的固定回归套件，仍预期342个目录ID和2093条断言；本体目录或被测行为改变后应先复核样例与预期，不能把旧数量当作永久规则。其最新结果位于[tmp/m006_history_engine_result.json](../../../tmp/m006_history_engine_result.json)，本轮收紧后的判定再次通过2093/0。

更换引擎、修改抽取方式、执行/判定逻辑或归档方式后，再做相应自检：

```powershell
python tools/check_isolated_engine_reliability.py
```

新机制需要自己的输入、预期和依赖说明，可以复用共享执行/判定模块，不能只改函数名便把旧测试数量当作覆盖证据。测试桩替代的部分、未覆盖的真实回调/菜单/保存路径须在报告中明确列出。

## 路径和生命周期

- 每次临时ERA工程位于项目`tmp/isolated_engine_runs/<运行标识>/`，采用本机引擎副本和`--ExeDir`，隐藏启动，并设置项目内的原生库解包目录。
- 本体/authoring只读；数据库用`mode=ro&immutable=1`读取目录快照，执行前后校验指纹。所有引擎配置、日志和测试数据均在项目内。
- 每个运行结束，包括本轮验证过的失败和超时情况，都归档ERB/ERH/ERD为`.fixture`并删除可执行副本，避免主游戏递归加载。异常中断后仍须检查是否有活动脚本或子进程残留。
- 目录和食谱基础数据与共同制作历史仍是不同内容；本轮没有修改游戏数据结构或清除旧记录。

2026-11-13原始M006结果另存为[m006_history_engine_result_20261113.json](../../../tmp/m006_history_engine_result_20261113.json)，不覆盖历史证据。它没有本轮新加入的完整判定元数据，可靠性结论以本轮报告及收紧后回归结果为准。

结论限于本机当前引擎、当前执行/抽取形式和已列正反例：可作为长期备选，不能据此宣称所有引擎版本、所有ERABASIC语法或完整游戏都已验证。当前抽取器按单行函数标签选取片段，条件编译/停用区域、宏和复杂声明仍需人工检查；指纹相同不等于已证明完整调用环境等价。预期值和测试桩本身的正确性也仍需审查。

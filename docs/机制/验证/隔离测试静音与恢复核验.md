# 隔离测试静音与恢复核验

日期：2026-11-14。用户不希望测试反例频繁发出报错提示音，随后明确允许为查验静音方法而发声。本轮已将静音守卫接入共享执行器，报错文本、日志、异常和失败判定均保留。

## 声音来源和采用的方法

本机引擎的错误路径会调用SystemSounds.Hand.Play；读取现有程序的元数据/IL确认ThrowError等位置直接触发系统提示音，没有找到独立的测试提示音配置开关。对应[.NET 8实现](https://raw.githubusercontent.com/dotnet/runtime/v8.0.0/src/libraries/System.Windows.Extensions/src/System/Media/SystemSound.cs)调用Windows MessageBeep。

实测单独静音调用进程的音频会话无效：进程自身峰值为0，系统提示音会话仍有约0.64的峰值。因此采用**临时静音Windows系统提示音会话，再恢复其原状态**；不修改游戏引擎、不改游戏BGM设置、系统主音量、普通应用音量或系统声效方案。

这意味着：测试期间其他Windows系统提示音也会一起静音。它是短期音频会话控制，不是永久关闭系统通知音。不能称为只屏蔽单个报错事件。

## 静音守卫

实现文件：

- [isolated_audio_guard.py](../../../tools/isolated_audio_guard.py)：启动/停止守卫及确认状态。
- [engine_system_sound_guard.ps1](../../../tools/engine_system_sound_guard.ps1)：独立恢复进程、互斥锁、父进程监视、状态文件。
- [engine_system_sound_guard.cs](../../../tools/engine_system_sound_guard.cs)：Core Audio会话枚举、Mute读回、原状态恢复和尾音检测。
- [isolated_engine_support.py](../../../tools/isolated_engine_support.py)：默认在发动引擎前取得静音确认，在引擎退出后停止守卫，将音频恢复错误纳入不通过条件。

只选择IsSystemSoundsSession为真的会话，保存各会话原Mute值，设为静音并读回确认。等待200ms让音频引擎应用静音后，才允许启动测试。原来已静音的会话最终仍保持静音。

测试结束或超时后，先确保测试引擎已退出，再等待提示音信号连续安静350ms（最多等待4秒），以免恢复时漏出尾音，最后恢复先前Mute状态并核对。找不到会话、无法确认静音或恢复不成功时，不静默降级为有声测试，也不把结果判为通过。

恢复进程脱离测试所有者的作业，监视所有者PID和进程开始时间；所有者异常消失时也会恢复，最长持有时间受85秒看门狗限制。命名互斥锁防止并发守卫互相覆盖原状态：当前隔离测试应串行运行；锁占用时拒绝新一轮发动，不争抢系统静音设置。

配置、编译临时文件、音频状态记录和日志均在项目tmp内。没有创建声音API补丁或改变引擎错误处理，不通过吞错实现静音。

## 音频探针

本轮在获准后实际调用MessageBeep，观察系统提示音会话和默认输出端点的数字电平。

在静音守卫已生效的探针中：

| 指标 | 结果 |
| --- | --- |
| 系统提示音会话峰值 | 约0.64015，说明提示音仍被产生 |
| 设备实际混音输出峰值 | 约2.33×10^-10，接近数字零 |
| 设备主音量标量 | 前后均0.3 |
| 设备主静音 | 前后均False |
| 两个系统提示音会话 | 静音期间为True，结束均恢复原False |

这是数字电平/状态验证，不是由助手作主观听感判断。证据：[mute_probe_result.json](../../../tmp/engine_audio_inspect/mute_probe_result.json)。探针初期发现需留出音频引擎应用时间，正式守卫因此在确认Mute后再等待200ms。

临时发声探针脚本及反编译/NAudio排查副本已在2026-11-14的tmp清理中移除，仅保留上面的数字电平JSON证据；它们不是常规测试依赖。以后需要重新作发声诊断时，先取得用户明确授权，再在项目内构造受控探针。常规测试默认走静音守卫。

## 恢复与回归结果

音频守卫四项检查均通过：

1. 正常结束恢复全部原Mute状态。
2. 并发守卫被拒绝，首个守卫仍正确恢复。
3. 测试所有者用os._exit直接退出、没有执行其清理逻辑，独立守卫仍恢复。
4. 原来已静音的状态不会被错误地恢复为有声；外层测试结束也还原最初状态。

入口：[check_isolated_audio_guard.py](../../../tools/check_isolated_audio_guard.py)；报告：[isolated_audio_guard_result.json](../../../tmp/isolated_audio_guard_result.json)。

静音默认启用后，18项执行器可靠性检查再次全部符合预期；所有实际启动的引擎场景都确认静音、尾音安静和恢复。故意语法错误、越界、零除等仍按原判定被拒绝，没有为静音降低告警级别或屏蔽错误日志。

原料理套件也再次执行2093项断言，0失败、正常退出，音频守卫报告restored且tail_quiet为True。结果分别见[可靠性报告](../../../tmp/isolated_engine_reliability_result.json)和[料理回归报告](../../../tmp/m006_history_engine_result.json)。

## 使用和边界

常规入口无需额外参数，默认静音：

```powershell
python tmp/m006_history_engine_check.py
```

音频控制或执行器有变更时，可按任务需要复核：

```powershell
python tools/check_isolated_audio_guard.py
python tools/check_isolated_engine_reliability.py
```

当前已验证本机Windows、现有两个活动输出端点和当前引擎。测试期间不应手动切换输出设备或争抢系统提示音Mute状态；设备热插拔、音频服务异常、守卫自身被强制杀死或系统断电不在本轮保证内。恢复未确认时，先查本次audio_guard.json并核对系统提示音状态，不能直接继续发动测试。

本轮没有修改业务ERB/ERH、游戏本体配置、正常存档或系统主音量。完整游戏联调、真实食谱解析和存读档仍保持此前未验证状态。

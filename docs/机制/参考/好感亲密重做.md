# 本体选项参考：好感亲密重做

核对日期：2026-11-12。本体提交667b9cd0b，工作树已有COMF495和emuera.config改动，本次未修改它们。仅阅读当前源码，未运行游戏、未读取存档，不能确定用户实际开关及PALAMLV状态。

用途：为本口上后续SOURCE、回忆/能力成长、好感信赖调校提供本体依赖参考，不另计为已实现的自定义机制。

用户决定：在R002日末快照保护设计中，不将这一选项的日末亲密附加修正作为需要兼容的约束；这不表示关闭全局选项或修改其本体实现。本次只记录机制。

## 开关与影响路径

变量 `MAGIC_DLC_好感亲密重做` 定义于 `ERB/DLC/魔法DLC/魔法相关参数.ERH:9`，为SAVEDATA，可随档保存。新建魔法DLC模式、部分预设及DLC菜单可设为1，菜单也可关闭。大多数分支只检查该变量，不额外检查MAGIC_DLC总开关；个别效果还需其他开关或状态。

不能将它理解成单一“亲密加速倍率”。主要路径是：SOURCE经过本体换算成为PALAM，再按档位结算成珠子，珠子用于能力升级；好感/信赖和积攒度则有另外的计算分支。

## 1. PALAM等级表与日末珠子结算

`ERB/初期設定.ERB:63～109` 的DEFAULT_OPTION依据当时开关设置两套PALAMLV；`ERB/イベント関連/AFTERTRA.ERB:713～833` 的JUEL_CHECK按当前开关选择珠子换算规则。

部分PALAMLV边界如下：

| 等级边界 | 关闭 | 开启 |
| --- | ---: | ---: |
| 1 | 100 | 100 |
| 2 | 500 | 200 |
| 3 | 3000 | 500 |
| 4 | 10000 | 1000 |
| 5 | 30000 | 2000 |
| 10 | 400000 | 100000 |
| 15 | 5000000 | 5000000 |
| 16 | 10000000 | 10000000 |
| 20 | 10000000 | 200000000 |
| 25 | 10000000 | 10000000000 |

在开关与对应初始PALAMLV表一致的前提下，单项PALAM的基础珠收益举例（非快感项目）：

| 当日累计PALAM | 关闭 | 开启 |
| --- | ---: | ---: |
| 2000 | 20 | 1000 |
| 10000 | 1000 | 3500 |
| 100000 | 5000 | 20000 |
| 10000000 | 150000 | 800000 |

关闭分支单项基础收益最高150000；开启分支扩展至最高200000000（达到PALAMLV:25后）。不是把所有收益统一乘一个倍率：低、中、高区间的变化不同。

快感类还追加EX×1000；否定类珠有单独汇总逻辑，因此上述示例不能直接套作所有项目的最终总收益。润滑也不是普通可累积珠项目。

PALAMLV同时被GETPALAMLV、绝顶阈值及大量状态条件读取，不只是珠子结算专用表。例如TRACHECK_ORGASM:752使用PALAMLV:4判定绝顶强度；若确实使用开启版表，该阈值也随之不同。不能只改珠收益而忽略共享表的其他读者。

### 当前源码的表同步限制

DLCCHIOSEMENU的开关分支（1276行起）只改MAGIC_DLC_好感亲密重做；当前未见在切换后重建PALAMLV的调用。可查到的整表初始化位于DEFAULT_OPTION，新档和周回调用它。本次检索未找到知识库提及的SET_PALAMLV_BY_MAGIC_DLC修复函数；知识库描述的修复不能作为当前本机已实现的结论。

正常NEWGAME先于模式选择调用DEFAULT_OPTION，模式选择随后又可开启该开关，亦存在开关与建表时点不同的可能。调校/复现时应记录实际PALAMLV:2、:4、:17、:25，不能只看开关值；本次没有读取运行值，不断言用户已经遇到异常收益。

### “没有生效”与“规则/参数失配”的区别

开关不是无效，而是直接读取开关的逻辑可以立即切换（例如升级费用、好感信赖加成、日末亲密补正），但珠收益规则所依赖的PALAMLV可能仍是另一套参数。JUEL_CHECK也会立即选择开启分支，只是该分支读取了残留阈值，形成混合状态。

可由当前源码直接算出的例子：PALAM=10000000时，正常关闭规则及关闭表得到150000基础珠；正常开启规则及开启表得到800000；开启规则配关闭表时，由于关闭表的PALAMLV:16及以后均为10000000，开启分支的所有严格小于比较最终落空，进入最高档，得到200000000。此例为源码推算，不是当前用户存档的实测结果，说明失配可能使收益异常放大而非没有变化。

已核实的时序是NEWGAME:9先按当时的开关建表，NEWGAME:44才进入NEWGAME_MAKE，其中NEWGAME_MAKE_SELECT_MODE:60可把开关改为1。游戏途中菜单也只赋开关，不重建表。尚未以实际运行值确认本机每种新档/读档组合的表内容。

关于PALAMLV存档属性，参考资料存在冲突：authoring知识笔记称其不保存，本地语言手册Emuera/variables.zh.md:445的表却标保存为○。本轮不凭任一笔记断言当前引擎的存读档属性；若要确认跨进程读档行为，需以后针对本机引擎实测。这个不确定项不影响“菜单切换代码未同步重建表”的源码结论。

## 2. 亲密、顺从与欲望升级需求

定义：`ERB/ステータス計算関連/ABL/ABL_UP_DATA.ERB`，JUEL_DEMAND_9:498、JUEL_DEMAND_10:606、JUEL_DEMAND_11:767附近。

亲密下一等级所需好意珠的基础量（未叠加特质和其他全局倍率）：

| 当前亲密→下一级 | 关闭 | 开启 |
| --- | ---: | ---: |
| 0→1 | 30 | 30 |
| 1→2 | 100 | 100 |
| 2→3 | 300 | 300 |
| 3→4 | 1500 | 1000 |
| 4→5 | 5000 | 3000 |
| 5→6 | 15000 | 10000 |
| 10→11 | 300000 | 150000 |
| 20→21 | 1300000 | 16000000 |

开启时高等级进入更陡的表，20之后基础量为40000×当前亲密²；关闭时10以上为100000×(当前亲密−7)。所以并非全阶段都更容易。

“难以越过的底线”对亲密需求仍有恋慕前翻倍、恋慕后通常减半的分支；开启时且同时拥有思慕/恋慕，会走一个不减半的空分支。体目当て另有倍率。亲密升级的EXP_DEMAND_9为0。

顺从的恭顺珠路线在低等级基本相同，高等级增加专门表和4000×顺从²尾段；恐怖珠路线没有这一开关分支。

欲望有不同珠路线：欲情珠（JUEL:11）路线没有该开关分支；另一条是JUEL:21，当前CSV名称为优越，开启后改用与亲密开启版同形的基础需求表（0级30、1级100、2级300等，20之后40000×欲望²）。恋慕、难以越过的底线和体目当て仍会继续修正需求。

注意：能力显示:1540将JUEL:21标为“欲情珠”，与当前CSV/palam.csv中的21“優越”不一致。核验及调数值时以变量编号和实际公式为准，不混淆JUEL:11与JUEL:21。

## 3. 本体好感与信赖增量

定义：`TRACHECK_好感度上昇処理.ERB` 的FAVOR_CALC:8；`TRACHECK_信頼度上昇処理.ERB` 的TRUST_CALC:8。以下是开关直接改变的局部步骤，不是最终完整公式；之后还有SOURCE、刻印、状态、失败判定及玩家倍率等修正。

### 好感

关闭时，恋慕通常加2，思慕加1，主角的魅力/魅惑/谜之魅力/人气等以各项固定加1处理。

开启后改为向当前TFLAG:97加：

```text
主角容姿×3 + 魅力×6 + 魅惑×4 + 谜之魅力 + 人气×2
```

随后依次对思慕×1.2、恋慕×1.5、恋人×1.5，满足多项可连续乘算，整数运算会截断。催情药相关加成在开启分支也保留。后续仍有原本的SOURCE作用、状态修正、失败/强行处理和好感上升率；最终本体好感限制在0～1000000。

### 信赖

关闭时，谜之魅力加1、恋慕加2、思慕加1。

开启后改为：

```text
当前增量 += 主角魅惑 + 谜之魅力×3 + 人气×2
当前增量 += (主角教养 + 1) / 2
恋慕×1.5；思慕×1.2；恋人×1.5（按源码顺序）
```

这些乘算发生在后续SOURCE修正之前；仍受其他状态、失败、助手、睡眠及上升率等逻辑影响。本体信赖最终限制在0～999999。

本口上在M011/M012中自行计算好感信赖，并借MARKCNG相关接口尝试接管结算；本轮不将上述本体公式直接当作燐的最终增量，实际接管覆盖范围需在M011/M012审查时核验。

## 4. 日末直接提高亲密

`ERB/イベント関連/EVENTTURNEND.ERB:22～27`：开关开启，信赖>0，好感>=1000000，且计算值高于当前亲密时：

```text
亲密 = SQRT(信赖) / 8
```

仅提高、不消耗珠、不改变欲望。用户已决定在R002保护设计中忽略这一特定影响。

## 5. 积攒度、欲求不满与关系系数

`ERB/DLC/魔法DLC/魔法相关函数.ERB:526` 的积攒度上限，关闭时返回1000，开启时按状态优先判断：

| 状态 | 上限 |
| --- | ---: |
| 恋人 | 9999 |
| 恋慕或爱欲 | 1000 |
| 思慕或炮友 | 700 |
| 其他 | 400 |

实际是否使用此函数取决于调用点；例如SOURCE.ERB:1201还区分MAGIC_DLC总开关。不能据函数返回值就断言所有路径已钳制到该上限。

接吻相关COM19/20/312在开启时追加 `亲密 + 2×欲望` 的积攒度，受上限限制。SOURCE.ERB:1177的欲求不满增量增加魅力魔法有效时的倍率分支，其余催情药/发情等分支仍存在。

TRACHECK_ORGASM:727：开启时积攒度达到1000/3000/5000/7000，高潮时消减欲求不满所用系数分别×1.5/2/2.5/3；与原有时停、发情等系数继续组合。

MAGIC_LoveFactor:565在关闭时返回0；开启时返回 `SQRT(MAX(欲望+亲密,10)×10)×关系分值×参数/30`。关系分值受清白交往、恋人、恋慕、思慕、爱欲、满好感、底线特质和反发刻印影响。该系数还被BASE自然变动、扫除、学习、调合等调用，用途不只增加积攒度；是否实际生效需结合调用方其他条件。

## 6. 指令与显示的其他直接分支

- COMMON_J.ERB:8：同时开启“大成功相关”和本开关时，亲密对成功率的贡献由 `MIN(亲密,10)×5` 改为 `MIN(亲密,20)+MIN(亲密,40)+MIN(亲密,60)+MIN(亲密,80)+亲密`。10以下两式相同；20时分别50/100，40时50/180。

- COMMON.ERB:2066：信赖显示评级中间档位发生变化，显示变化不等于直接修改信赖值。
- 能力表示.ERB:1538：增加当前珠数/升级需求显示；JUEL:21标签问题见前文。

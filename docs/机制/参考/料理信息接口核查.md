## 当前结论

1. **当前制作的料理可以直接取编号。** COM413在成品制作前写入`FLAG:料理`（FLAG20），成功后才进入口上EXTRASOURCE；本口上当前记录点不必逐菜调用DISHDATA再用名字反查。
2. **本体已有QOL料理数据库和按ID取字段的接口。** 适合获取目录和基础资料；它保存配方资料，不是玩家/角色共同制作历史，不能替代本口上的经历记录。
3. **基础资料与实际料理实例须分开。** QOL GET接口不应用动态名称、节令/地点变化和剧本自定义菜单覆写；这些由DISHDATA及烹饪路径在运行时应用。当前实例的DISH_NAME等应在适当时点直接读取。
4. **前次数量统计更正为183种正式普通料理、漏收14种。** 本体源码与当前只读缓存一致；此前180/11的统计漏掉4条带行尾注释的CASE，并混入DEBUG专用299。完整纠正见下文。
5. 旧`AME36_DISH_INDEX`还输出RESULT:1的自定义菜单识别信息，调用者将其编码到TFLAG分支值；未来替换获取编号的方式时须单独保留或明确替代该职责，不能仅删整个函数调用。

以上是源码核对和数据库只读快照，不是游戏运行验证。

## 当前料理编号的生产、保留与读取时点

本体路径以下相对`F:/eratw/`。

`CSV/FLAG.csv:29`定义20为“料理”。`ERB/コマンド関連/COMF/日常系/COMF413 料理を作る.ERB @COM413:6`的正常制作路径：

1. 263行确认选择和素材，265调用DISHDATA，266～268要求返回10（可制作）。
2. 269～274将食材口味等应用到运行时字段，设置旧展示名DISHNAME。
3. **275行将已选料理ID存到FLAG:料理，276才清SELECT_MENU。** 因此不能去取已清零的菜单私有变量，应读取成品编号。
4. 278调用DISH_COOKING，正常分支405返回1；该计算处理味道、评分、食材、助手等，不把FLAG料理编号改成评分或类别。
5. `ERB/ステータス計算関連/SOURCE/SOURCE.ERB:131`先CALL_COM，139～145按返回值判断中止/跳过，147才发EXTRASOURCE。此时本口上的`AME36_EXTRASOURCE_GENERAL` CASE413可以读到上面写入的ID。

正常制作路径中，超级幽幽子事件等可使COM413返回-1，SOURCE便不会进入这次EXTRASOURCE；本轮只说明当前成功入口的数据可用性，不调整这些取得边界。

`COOKING_UI.ERB @RESET_DISH:511`在526清FLAG:料理，同时清DISH_NAME、DISHNAME、DISH_ASSI等。它会在取消、其他料理操作和部分后续流程调用；所以这个槽表示**当前料理实例**，不能拿它当历次制作记录。`EVENTCOMEND2.ERB @TURN_RESET:57～59`按料理重置标签清成品；COM413_TAGS:712当前只设置偷吃禁止、家事标签，没有料理重置标签。COM413成功进入EXTRASOURCE之前的有效性已经由上述顺序核对，仍不能保证任意晚期回调都持有旧成品。

旁路生产例子：`COMF498 調理の鉄人.ERB:289`也写所选菜单ID；`COOKING_UI.ERB @料理生成:603`在617写生成结果ID。这里只确认编号语义一致，不将这些路径自动纳入本口上的共同制作收集范围。

FLAG是全局当前实例编号；本口上位图则是省略角色维的CFLAG，属于当前TARGET。读全局ID不需要切换TARGET；是否由阿燐参与、何时写她的经历仍由现有回调和门控决定。本轮不把“知道料理编号”扩大为“所有生成或独自制作都应记给阿燐”。

## QOL数据库提供了什么

`ERB/魔改内容/qol/qol_dish.ERB`：

| 接口/入口 | 行号 | 实际用途与副作用 |
| --- | --- | --- |
| QOL_DISH_INIT | 93 | 连接plugins/qol_data.db，建表、比版本并可能重新注册；不是普通查询，口上无需自行调用 |
| QOL_DISH_DATA_REGISTER | 135 | 遍历普通料理、登记角色料理、写动态标志和版本，写数据库；本轮未调用 |
| QOL_DISH_REGISTER_CHARA | 173 | 调用原生SPECIAL_MENU编号函数登记基础角色料理；不在这里登记每个剧本的菜单覆写 |
| QOL_DISH_HAS_DATA(id) | 212 | 只读存在性查询 |
| QOL_DISH_GET_NAME(id) | 224 | 只读缓存的基础源名 |
| QOL_DISH_GET_TASTE(id) | 237 | 只读缓存的基础口味 |
| QOL_DISH_GET_COMMENT(id) | 250 | 只读基础说明 |
| QOL_DISH_GET_TYPE(id) | 263 | 只读分类，如轻食、主食、甜点 |
| QOL_DISH_GET_TIME / GET_MAXLIMIT / GET_SKILL_LV | 276/288/300 | 只读基础耗时、保质上限、技能门槛 |
| QOL_DISH_HAS_DYNAMIC(id) | 312 | 只读是否需要动态处理 |
| QOL_DISH_RESOLVE_ING(id) | 325 | 将缓存食材解析写到全局DISH_ING，不能视为无副作用查询 |
| QOL_DISH_DYNAMIC(id) | 353 | 按当前环境修改全局DISH_TASTE、DISH_NAME或DISH_COMMENT，不写库 |

上述GET/存在性函数使用参数化SELECT和函数自身LOCAL(S)，没有改DISH_*全局字段、TARGET或经历记录。数据库表的键是dish_id，其他列是名称、口味、材料、时间、分类、技能、动态标记等；没有共同制作角色、次数或完成日期字段。`FOOD.ERH`保存的是当前料理各字段；`LEARNED_MENU`及`LEARNING_SP_DISH`记录固有食谱学习进度/学会日期，也不是各道菜与阿燐共同制作的收集历史。

初始化链为`TITLE.ERB:27 → QOL_DB_INIT:46（qol_db.ERB）→ 52 QOL_DISH_INIT`。现目录里没有独立的“返回全部普通料理ID列表”封装；本体`QOL_DISH_DEBUG_DUMP:464`示范按ID排序的SELECT reader。未来查询界面可评估从现有库枚举ID，而不是再维护一套易落后的菜单区间。该建议不要求调用注册、重建或修改数据库。

## 缓存基础资料与运行时覆写的差别

`DISHDATA.ERB @DISHDATA:10`：

- 18～25先清/重建若干DISH_*运行时字段。
- 28～36有QOL数据就取基础字段。
- 37～39需要动态处理时调用QOL_DISH_DYNAMIC。
- 40～47对于角色料理再调用KOJO_CHECK(..., "CHARADATA", "SPECIAL_MENU")，应用当前所选剧本的覆写或禁用。
- 无缓存记录时49调用DISHDATA_ORIGINAL；之后还有季节、材料和可制作性处理，RESULT/RESULTS也作为输出。

所以DISHDATA依然是解析**当前有效食谱**的入口，但不是轻量、无状态的读取函数。它会调用其他角色的CHARADATA CHECK，CHECK分发暂时改变TARGET并在正常返回恢复；被调用的剧本可能有自己的副作用。本口上旧反查每试一个ID都执行这套过程，随后还要备份恢复料理全局字段；只为取得已经存在的当前ID，没有必要做这次遍历。

两个具体例子：

- **345号料理**：缓存基础名是Tarte Soleil；QOL_DISH_DYNAMIC:415～422按地点改成Tarte Lune或Tarte Soleil。二者仍是同一ID，不能按缓存名代替当前成品名，或把名称变化当作新增料理编号。
- **436号料理**：当前缓存基础名是“烤腐肉”，来自`キャラデータ/Chara_data_36_お燐.ERB @SPECIAL_MENU_36:149`；本口上`自定义机制_杂项.ERB @M_KOJO_AME_CHECK_K36_CHARADATA:175`在333～339覆写成“琥珀渔夫派”。单独调用QOL_DISH_GET_NAME(436)不会获得这一覆写；正常DISHDATA路径会检查CHARADATA。

因此：记录当前制作哪道菜优先用成品ID；需要这次实际名称/口味时读取当前实例字段；展示不依赖环境的基础目录可用QOL GET；需要实时自定义/动态食谱时再按需解析DISHDATA并管理其副作用。`DISHNAME_TR`是显示翻译层，不能替代料理身份编号。

## 旧反查函数不能整段机械删除

当前项目`工具函数.ERB @AME36_DISH_INDEX:614`（行号已随用户注释整理变化）：

- 642清RESULT；643～647对于角色料理调用原生SPECIAL_MENU，并将与实际名称不同的情况记到RESULT:1。

直接读取FLAG编号可以替代“当前是哪一道”的遍历；**自定义菜单标记是另一项职责**，须在后续修复时单独保留或明确替代。当前编号相同并不提供“原生/剧本覆写”这一额外标记。也不建议改调本体`COOKING_UI.ERB @料理番号出力:662`：它同样遍历按名匹配，而且普通调用676～677会RESET_DISH，直接清当前成品编号与数据，副作用更不适合这个记录点。
